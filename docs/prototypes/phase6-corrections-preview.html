Payroll Staff — payroll:entry only

  • Sees the Corrections sidebar item and the Corrections Ledger tab
  • Does not see the Review Queue tab at all
  • Can submit a Correction Request from a Released/Archived Payroll Entry
  • Cannot approve, reject, or record a settlement

Reviewer — corrections:approve only, no payroll:entry

  • Sees the Corrections sidebar item (Phase 6 Checkpoint 6A fix — an OR-permission check, not payroll:entry alone)
  • Lands on the Review Queue tab by default; the Ledger tab is also visible
  • Can approve or reject any request within their assigned sites
  • Cannot open "Request Correction" from a Payroll Entry — that action stays gated on payroll:entry

Master Admin — every permission, unrestricted site scope

  • Full access to both tabs, every action, every site
  • May also correct a released entry directly, bypassing the request/approval split entirely, since they are already the approver

Unauthorized — neither permission

You do not have access to Corrections

Ask a Master User for the corrections:approve or payroll:entry permission.

No sidebar item, no direct-URL access, and every backend route rejects the same session with 403 independently of the UI.

Generated 2026-07-19 for Phase 6 Checkpoint 7A (Prototype Completion & UX Documentation) from frontend/src/routes/corrections-page.tsx, correction-request-detail-page.tsx, balance-adjustment-detail-page.tsx, frontend/src/components/corrections/* (four modals + correction-labels.ts), and backend/src/modules/corrections/ — reflecting the fully implemented, closed Phase 6 (Checkpoints 1 through 7).

This is a documentation/UX checkpoint only — no production code changed. Every screen above reproduces an already-implemented view; nothing here was designed fresh. Where the checkpoint brief's own requested table columns diverged from what the live UI actually renders (Materialization History's "Payroll Entry"/"Trigger" columns; Settlement History's "Remaining after settlement" column), the implemented columns were used instead, with a caption explaining where that data actually lives (audit metadata, or the parent record's own live aggregate) — consistent with this checkpoint's own "represent only implemented functionality, do not invent features" instruction.

Real behavior this preview deliberately does not reproduce: live preview debouncing (400ms, race-safe supersession of stale requests), the reservation-aware availableForStandaloneSettlement ceiling recomputed from two live-fetched figures, real permission-gated data fetching (TanStack Query), and the backend's own fresh transactional validation on every write — this file has no backend, no API, and no persistence, by design.

Status semantics reproduced exactly (correction-labels.ts): CorrectionRequestStatus PENDING=amber, APPROVED=green, REJECTED=red; BalanceAdjustmentStatus PENDING=amber, SETTLED=green; BalanceAdjustmentType PAYABLE=blue, RECOVERY=purple, NONE=gray (NONE is unreachable through the ordinary approval workflow — ZERO_DELTA rejects it outright before any row is created, shown in the Preview screen above); MaterializationStatus ACTIVE=amber, CONSUMED=green, CANCELLED=gray (CANCELLED has no real example — no code path creates one as of Checkpoint 7, shown here only as a disabled placeholder row for completeness of the closed enum).

Phase 6 Checkpoint 7's own contribution — the ACTIVE -> CONSUMED materialization transition, wired into releaseProjectUnit — has no dedicated new UI surface of its own; it is visible here exactly as it is in the live app, as a CONSUMED row in Materializations (screen 8) and a corresponding Cycle-Scoped Settlement row in Settlement History (screen 9), once the reserving cycle actually releases.
