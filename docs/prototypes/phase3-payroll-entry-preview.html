Updated 2026-07-11 for the Employee/Payroll Entry/Bank Sheet banking refinement: Account Title is removed entirely from this grid — it is no longer stored on `PayrollEntry` at all; the employee's own legal name is always the account holder (Bank Sheet alone still shows a derived "Title of Account" column, computed from the entry's employee name, never a separately stored field — see phase4-bank-sheets-preview.html). Corrected 2026-07-12 — the 2026-07-11 width increase alone did not fix the underlying defect. Root cause: the real grid's Bank <select> (payroll-entry-row.tsx) was rendering only bank.code (e.g. "MCB", a genuinely separate, short abbreviation field) instead of the full configured bank.name — no column width could have fixed that, since the *displayed value itself* was never the long string in the first place. Fixed to show "{bank.name} ({bank.code})", matching Employee Registry's own established convention — reproduced here as "Muslim Commercial Bank (MCB)" / "Habib Bank Limited (HBL)", not the bare codes this file previously (incorrectly) mirrored. Separately, ReadOnlyCell's unconditional Tailwind truncate class was silently ellipsis-clipping Employee Code specifically — fixed with an opt-out, since ellipsis is exactly the "hidden overflow" the permanent rule forbids for that field. Row 1's IBAN is now the exact canonical test value PK36SCBL0000001123456702; Row 2's Account Number was lengthened to 20 digits to demonstrate a realistic long value, not just a short one that always fit anyway. Columns widened again, this time from an explicit character-width budget rather than a guess (columns.ts's own comment shows the math): Employee Code 100→140, Bank 120→280 (now rendering "name (code)", needs real room), Branch Code 110→140, Account No. 190→260, IBAN 200→300 — each with deliberate margin above the minimum, not a bare fit. This static file's own CSS mirrors the same widths via explicit min-width rules (see the stylesheet), since a plain <table>'s auto-layout sizes an <input>-holding column by the input's default ~20-character intrinsic size, not by its actual value's length — the same category of "looks unconstrained but isn't" trap the real component's fixed-pixel CSS Grid tracks don't have, but worth guarding here too so this prototype can't silently drift back out of sync with what it claims to demonstrate.

Reversed 2026-07-13 — two architectural corrections, superseding the 2026-07-12 entry above. (1) Bank Code only, not "{name} (code)". The Master User defines both a Bank Name and a Bank Code (Settings → Banks); a dense transaction grid displays the Code specifically so the column stays compact without losing meaning — that is the Code's whole purpose. The full Name remains useful in Employee Registry's own dropdown, where a user is actively picking a bank and needs the context; it was never appropriate for this grid, and the 2026-07-12 fix above was itself the wrong direction, not merely incomplete. Reproduced here as "MCB" (Row 1) and "HABIBMETRO" (Row 2 — a 10-character code, the exact real maximum Bank.code varchar(10) permits, chosen specifically to demonstrate the dynamic calculation actually growing the column for a long *code*, not a long name). (2) No manually assigned pixel widths, guessed or generous. Every business-identifier column in the real grid (columns.ts) now computes its own width at runtime from the header and the longest value in the *entire loaded dataset* (`measureColumnWidth`, `computeColumnWidths`) — this file's own CSS mirrors that by switching from hand-picked min-width numbers to genuine browser-native content sizing (table-layout: auto; width: max-content; min-width: 100%), with each identifier input's size attribute set to its real value's length so the table's own auto-layout algorithm sizes the column from that value directly, not its input's ~20-character default — the dynamic-sizing equivalent of the real grid's per-entry measurement, expressed in plain HTML/CSS since this file has no JavaScript width calculation to run.
