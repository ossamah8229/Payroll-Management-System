Generated 2026-07-12 for Phase 4 Checkpoints 6.1–6.3 (Payslips: backend foundation, PDF Engine, Frontend/Batch Generation/Close-Out) from frontend/src/routes/payslips-page.tsx, frontend/src/hooks/use-payslips.ts, backend/src/modules/payslips/, and backend/src/lib/pdf/.

Scope, matching the implemented checkpoints exactly: a dedicated payslips:view permission (Master Admin, Payroll Staff, Finance) — never a reuse of payroll:entry/payroll:view/bank-sheets:view, since an individual Payslip discloses one employee's own net-salary breakdown, materially more sensitive than any aggregate sheet. Individual PDF preview/download reuses the single-PDF endpoint directly (?disposition=inline|attachment) — no second HTML template. Batch generation is bounded, stateless ZIP streaming (archiver, a warm shared Puppeteer browser, bounded render concurrency) capped at exactly 300 Payslips per request (MAX_BATCH_PAYSLIPS_PER_REQUEST) — never a queue, job table, or persisted archive. A single employee's render failure never aborts the batch; the resulting ZIP gains a _summary.txt naming any failures by employee code/id only (never a stack trace, SQL detail, or filesystem path). One payslip.batch_exported Audit Log entry is written per batch request (never one per employee); the existing payslip.exported action stays reserved for the single-PDF endpoint alone.

Explicitly deferred, not silently carried into this phase or the next without saying so: a genuinely company-wide "generate every Payslip in the cycle at once" archive is Phase 5's job (BackupPackage/StorageProvider, a persisted artifact, not yet built) — this checkpoint's batch endpoint is for realistic, operator-filtered selections up to the 300 cap, not an unconditional whole-company export. CompanySettings is read live at render time, not snapshotted (an accepted, documented gap, same category as the pre-6.1 employee-name gap it closed). Employee Statements remain Phase 7 scope, unaffected by any of this work.
