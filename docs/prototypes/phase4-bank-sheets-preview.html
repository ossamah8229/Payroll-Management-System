Generated 2026-07-11 for Phase 4 Checkpoint 3 (Bank Sheets) from frontend/src/routes/bank-sheet-page.tsx, frontend/src/hooks/use-bank-sheet.ts, and backend/src/modules/bank-sheets/.

Scope, matching the implemented checkpoint exactly: Bank Sheets are generated exclusively from released payroll (PayrollEntry.released = true, set only by the existing per-Project-Unit release sweep, Checkpoint 2 — the release boundary itself was not reopened or redesigned) and filtered by Bank (every active Bank) or Cash — one unified feature, not a separate Cash Receiving module. CSV and Excel export reuse this project's existing ExcelJS/csv-stringify convention, no second export framework. PayrollUnitReadiness, Late Entry release, Employee Statements, Reports, Dashboard work, and any Phase 5 functionality are all explicitly out of scope and not depicted here.

Every value on a Bank Sheet row — bank, branch code, account number, IBAN, designation, net salary — is read exclusively from the released PayrollEntry's own frozen columns, never from Employee's live record (Employee name/CNIC, and — since the 2026-07-11 banking refinement below — the derived Account Title, are the exceptions, matching every other export already in this codebase, since PayrollEntry never copied those). Verified directly in backend/tests/bank-sheets.test.ts: changing an employee's bank, account number, and designation after release leaves a previously generated Bank Sheet byte-for-byte unchanged.

Two real defects found and fixed via this checkpoint's own real-stack Playwright pass, not shipped: (1) the totals row was originally styled position: sticky; bottom: 0, intending to pin it to the bottom of the table's horizontal-scroll container — but that container only scrolls horizontally, so the row had no bounded vertical scrolling ancestor to stick to and instead detached and floated at the page's own viewport edge. Fixed to a plain, non-sticky footer row (reflected in this prototype's own CSS). (2) A genuine, pre-existing Employee Registry bug, unrelated to Bank Sheets itself: the "New Employee" modal (employees-page.tsx's EmployeeFormModal) stays mounted between opens (only its "Edit" sibling instance remounts fresh), so its form state — bank, account number, designation, gross pay, every field — silently carried over from one employee creation to the next unless manually cleared. Caught because Bank Sheet verification depends on creating two employees with different banks back-to-back; fixed with a reset-on-open effect.

Updated 2026-07-11 for the Employee/Payroll Entry/Bank Sheet banking refinement: Account Title is no longer a stored field anywhere — the frozen client Bank Sheet format (reference/PROJECT_SPEC.md, "Sample Bank Sheet Format") still requires a "Title of Account" column, so it survives here, but as a **derived** value only, always exactly the row's own entry.employee.name — read live, the same already-established exception noted above for Employee Name/CNIC, never re-introducing a stored/editable Account Title column. This holds for Cash rows too (see Imran Sheikh below): Account Title reflects the employee's name regardless of bank status, since it was never tied to having a bank account in the first place. IBAN is added as a new column (optional — many employees operationally don't have one on file, shown as "—" for Sana Tariq/Usman Farooq below) between Account Number and Account Title, in both the on-screen table and the CSV/Excel export headers; the Excel export's column widths (bank-sheets.service.ts) were extended to every business-critical identifier per the new permanent Layout Integrity Rule, not just Account Number as before.

Corrected 2026-07-12: Bilal Ahmed's IBAN is now the exact canonical test value (PK36SCBL0000001123456702), not an invented one — this table already rendered plain text (not an editable <input>), a full bank.name (never a bare code), and used white-space: nowrap with no truncate/overflow- hidden and no fixed per-column pixel widths, so it was already structurally safe from the defect found and fixed in Payroll Entry's grid this session (a <select> showing only bank.code, and a truncate class silently clipping Employee Code) — see phase3-payroll-entry-preview.html's footer for the full root-cause account. The Excel export's own column widths were widened further this same session (Bank 20→32, Account Number 24→30, IBAN 30→36) with explicit margin, not a bare fit — see bank-sheets.service.ts.

Reversed 2026-07-13, superseding the "full bank.name (never a bare code)" claim above. Two corrections: (1) the table's Bank column now shows the Bank Code ("HBL"), not the Bank Name ("Habib Bank Limited") — the approved Bank display rule, matching Payroll Entry's identical correction; the "Bank" *filter dropdown* above the table keeps the full name unchanged, since that is a selection control (the same "clarity is useful" treatment as Employee Registry's own dropdown), not a dense grid cell. (2) The table's fixed min-width: 1320px is replaced with natural table-layout: auto sizing (width: max-content; min-width: 100%) — it never caused clipping (this table holds plain text, not `<input>`s, so it was never subject to the intrinsic-sizing trap Payroll Entry's grid has), but the exact pixel number was still an arbitrary, manually-chosen one the permanent Dynamic Width Rule no longer permits, even when harmless. The Excel export's column widths (still necessarily fixed numbers — ExcelJS has no native content-driven auto-width) are computed from each export's own actual data (`excelColumnWidth`, `bank-sheets.service.ts`), not the generous-but-manually-chosen constants noted in the paragraph above.
