Finalize July 2026

Every payroll entry must be either released or held before finalization.

Finalization is a one-way lifecycle action — once finalized, this cycle moves from Draft to Released and per-Unit release actions are disabled. Held employees are not paid by finalization; it does not release them, generate a backup, or start the next payroll cycle. Archiving and starting the next cycle happen later, as their own separate steps.

Historical Payroll Cycle Selector

The shared selector

Every cycle-aware page (Payroll Entry, Salary Release, Bank Sheet, Cash Receiving, Payslips) composes the same two small pieces into its own existing header, rather than a new page shape:

July 2026 · Draft

PayrollCycleStatusBadge — a consistent label + status badge (green Draft, blue Released, gray Archived). PayrollCycleSelectField — a plain, keyboard-accessible native <select>, newest cycle first. No search or virtualization — cycle counts stay in the dozens even after years of operation.

Default resolution and routing

On first load (no cycle specified in the URL), a page resolves the default cycle in order: the Draft cycle if one exists, else the newest Released cycle, else the newest Archived cycle, else an empty state — never an arbitrary or unspecified cycle.

Every cycle-aware page is mounted at two paths rendering the same component: the original flat path (e.g. /payroll-entry, kept as a compatibility redirect that resolves the default cycle and navigates to the canonical URL) and the canonical /payroll-cycles/:cycleId/payroll-entry path a bookmark, refresh, or browser back/forward can target directly.

Frontend action safety

A confirmation modal (Release/Finalize/Rollover) open for one selected cycle is cleared automatically if the underlying cycle selection changes beneath it — e.g. via browser back/forward while the modal is still open — so an action can never accidentally target a different cycle than the one it was opened against.

Backup Package lifecycle

What actually ships in Phase 5

A Backup Package is generated automatically, server-side, as part of the Rollover transaction (the "Start New Payroll Cycle" action, shown in an earlier tab) — never a separately-triggered action a user initiates on its own. One package version is reserved before the archive transaction opens, its files (payroll entry data, manifest) are written to the configured StorageProvider (backend/src/lib/storage/ — local filesystem today, portable to any self-hosted target), and the package is marked Ready and linked to the now-Archived cycle in the same database transaction that performs the archive itself.

Generating → Ready

(or Failed, with the triggering rollover attempt itself rolled back — a Backup Package is never left half-written)

What this tab deliberately does not show

There is no dedicated frontend page for browsing, listing, or downloading Backup Packages yet. The backend API (GET/POST /api/v1/payroll-cycles/:cycleId/backup-packages, GET /api/v1/backup-packages/:id/files/:fileId) exists and is fully tested, but Phase 5's own frozen scope only wired it into the automatic rollover flow above — a management UI is not part of any phase's shipped scope yet. This screen intentionally shows that gap rather than a UI that doesn't exist in the real application.

Scope, matching the implemented phase exactly: Finalize (Checkpoint 1) moves a Draft cycle to Released — a one-way action, gated on payroll-cycle:manage, that does not release held entries, generate a backup, or touch the next cycle. Archive & Rollover (Checkpoint 3) is one atomic transaction: a fresh Backup Package is generated, the outgoing Released cycle becomes Archived and permanently read-only everywhere in the app, and a new Draft cycle for the next calendar month is created and bootstrapped automatically — there is no manual "create cycle" step distinct from rollover once a first cycle exists. The Historical Payroll Cycle Selector (Checkpoint 4) is the shared, two-piece component every cycle-aware page composes into its own header, with the dual flat/canonical URL scheme and default-resolution order described in the "Historical Cycle Selector" tab above.

Known, documented gaps carried forward unchanged by this phase (see docs/architecture/workflows/payroll-lifecycle.md §4–§5): there is no post-finalization release path for a still-held entry yet; Payslip PDFs and an Audit Log export are not included inside a Backup Package; Backup Packages have no dedicated browsing/download UI (see the "Backup Package lifecycle" tab above) — the automatic generation-on-rollover path is the entirety of this phase's frozen UI-facing scope for that feature.
