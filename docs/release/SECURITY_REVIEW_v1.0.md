# Version 1.0 — Release Security Review

Focused review against the RC1 checklist, performed against the running production build
(`NODE_ENV=production`, behind a local proxy simulating Render's TLS-terminating edge — see
`RC1_VALIDATION_REPORT.md` Step 6) on 2026-07-19/20. This is a review of existing protections, not a
new security architecture — no new controls were designed in this checkpoint.

## Checklist results

| Item | Result | Evidence |
|---|---|---|
| Password hashes never appear in responses | **Pass** | Live check: `GET /api/v1/auth/me` and `GET /api/v1/users` responses grepped for `passwordHash` — absent from both. Also backend-test-enforced: Phase 5 Checkpoint 4 close-out fixed and now regression-tests a `passwordHash` response-serialization leak found in the Users module at that time (`docs/PROJECT_PROGRESS.md`); `tests/payroll-lifecycle-response-security.test.ts` asserts no sensitive keys appear anywhere in cycle/backup-package responses. |
| Authentication required where expected | **Pass** | Live check: unauthenticated `GET /api/v1/employees` → `401`. `attachUser`/`requireAuth` middleware gate every non-`/health`, non-`/auth/login` route. |
| Permission checks exist on every protected endpoint | **Pass** (existing coverage, not newly audited route-by-route this checkpoint) | Every route module uses `requirePermission(...)`; `rbac.test.ts` passes; Playwright spec `07-corrections.spec.ts` Scenario 6 specifically proves a reviewer-only user (`corrections:approve` without `payroll:entry`) is boundary-enforced through the real UI, not just the API. |
| CSRF protections remain active | **Pass** | Double-submit cookie (`common/middleware/csrf.ts`) verified live: every state-changing call in the RC1 lifecycle smoke test required a matching `x-csrf-token` header; login without it returns `403`. |
| Production cookies use appropriate security settings | **Pass, with one operational dependency to flag** | Live-verified: in `NODE_ENV=production`, session and CSRF cookies are `Secure`, session is additionally `HttpOnly`, both `SameSite=Lax`. **`express-session` will not set the session cookie at all unless the connection is provably HTTPS** (via `req.secure` or `X-Forwarded-Proto` with `trust proxy` — already configured). This means the backend must never be reachable by real users over plain HTTP; it must always sit behind a TLS-terminating proxy (Render's default topology satisfies this). Documented in `CONFIGURATION_REFERENCE.md`. |
| Malformed UUIDs return controlled errors | **Pass** | Live check: `GET /api/v1/employees/not-a-valid-uuid` → `400 {"error":{"code":"VALIDATION_ERROR",...}}`, no stack trace or internal detail. |
| Database errors do not leak sensitive details | **Pass** | The one real production-mode error surfaced during this checkpoint (`relation "session" does not exist`, see the Step 2/6 findings) returned a generic `500` to the client with no SQL, table, or connection-string detail in the HTTP response — the detail was only in the server-side log, as intended by `errorHandler`. |
| Storage keys are not exposed in sanitized API responses | **Pass** | Live check: `GET /api/v1/backup-packages/:id` response grepped for `storageKey` — absent. | Private backup files are not publicly browsable | **Pass** | Files are served only via `GET /api/v1/backup-packages/files/:fileId`, which is permission-gated and resolves through the `StorageProvider` abstraction — there is no static file route serving `STORAGE_ROOT` directly (confirmed: no `express.static` mount over the storage directory in `app.ts`). |
| CSV formula injection protection remains active | **Pass** | `tests/csv-formula-injection.test.ts` passes in the full backend suite (part of the 791/791 run this checkpoint). |
| User-controlled filenames cannot escape storage boundaries | **Pass** (existing coverage) | `LocalFilesystemStorageProvider` (`docs/architecture/system-conventions.md §2`) resolves all keys under `STORAGE_ROOT`; `storage.test.ts` passes. Not re-audited path-by-path this checkpoint beyond the existing test coverage. |

## Flagged for the known-issues register (not RC1 blockers, but worth explicit tracking)

1. **Cross-site cookie risk in the real Render topology, unverified against an actual Render deployment.** `render.yaml` configures the frontend and backend as two independent Render services, each getting its own `*.onrender.com` subdomain. `onrender.com` is registered on the Public Suffix List specifically so that subdomains of it are treated as separate *sites* by browsers, not merely separate origins on the same site. Session/CSRF cookies are `SameSite=Lax`. Lax cookies are not attached to cross-*site* `fetch`/`XHR` requests (only to top-level navigations) — if this holds for two independent `onrender.com` subdomains the way it does for two unrelated domains, authenticated API calls from the deployed frontend to the deployed backend could fail entirely in a genuine Render deployment. This is analytically derived from the cookie configuration and standard, well-documented browser behavior (not observed as a live failure, since a real cross-site deployment was not available to test in this sandbox — same access constraint already noted for Phase 4's outstanding Render smoke-test condition). **Recommended pre-production action**: verify this specific behavior against a real Render deployment before the actual `v1.0.0` production cutover; if it does break, the fix is one of (a) a shared custom parent domain for both services, (b) fronting both behind one reverse-proxy origin, or (c) switching cookies to `SameSite=None; Secure` for the cross-site case. Not an RC1 blocker because RC1's own UAT environment can be deployed same-site (e.g., both services behind one reverse proxy, or tested locally as this checkpoint did).
2. **No cloud `StorageProvider` implementation exists yet** — only `LocalFilesystemStorageProvider`. Production backup-package files and any future uploads currently have no durable-storage story beyond the application server's own local disk. See Known Issues register.

## Explicitly out of scope for this review

Per the RC1 core rule, this was a review of *existing* protections, not a new hardening project. A full RBAC re-verification across every single route (Phase 9's own stated scope) was not repeated route-by-route beyond the existing automated coverage (`rbac.test.ts`, permission-boundary tests throughout the backend suite, and the Playwright corrections-boundary scenario). No new security controls were added.
